# 0007: Three steps, one decision in Schrijver, four eyes

Date: 2026-10-10. Status: accepted. Builds on [0005](0005-no-approve-from-schrijver.md).

## Context

The owner looked at a sent-in proposal as a member of the redactie and could not tell what to do: the text said the next step was approving on GitHub, the only button said Samenvoegen. Schrijver cannot approve (decision 0005) but can merge, so the page showed two verbs for one decision and a step "Goedgekeurd" that Schrijver lets you skip. Nine separate things sat above the fold, three of them about GitHub. A comment of the redactie went to GitHub and never came back, and comments and reviews placed on GitHub were not shown: a writer whose proposal needed changes could not read what to change. Nothing kept a member of the redactie from merging their own proposal.

## Decision

1. **Three steps.** Concept, Ingestuurd, Samengevoegd. A proposal that is sent in, approved on GitHub or waiting for an adjustment is on Ingestuurd; a closed one has no step.
2. **One decision in Schrijver.** A member of the redactie merges ("Samenvoegen") or asks for an adjustment ("Vraag om aanpassing"). Whether the site asks for an approval on GitHub first comes from GitHub, as the pull request's `reviewDecision`, read only by the proposal page and the merge; where one is missing the page says so, and when GitHub cannot tell, the merge is tried and GitHub's refusal speaks. Where Schrijver does not merge, the page sends the redactie to GitHub: where the site setting "Samenvoegen in Schrijver" is off, and where the proposal has as many commits as GitHub lists (250), which Schrijver cannot check as a whole. Where GitHub cannot merge the proposal because the page changed on the site since, the page offers no merge either.
3. **Aanpassing gevraagd is a label.** The App cannot submit a review as the person (decision 0005), so "Vraag om aanpassing" posts the request as a comment and sets the label `aanpassing gevraagd`; "Opnieuw insturen", which only the writer has, takes it off. A changes-requested review on GitHub counts the same: the proposal stays on Aanpassing gevraagd until every reviewer who asked for changes is asked to review again, and "Opnieuw insturen" asks each of them (GitHub's re-request of a review); their change request stays on GitHub until they review again there. Both ways "Opnieuw insturen" comments "Klaar voor beoordeling". Te beoordelen counts what lies with the redactie: sent in or approved, without the reader's own proposals where four eyes keep them from deciding.
4. **The conversation comes into Schrijver.** Every comment and review of the pull request shows on the proposal page, in time order, rendered through the Markdown preview pipeline. The writer and the redactie react from Schrijver; the App posts the reaction with a hidden marker and one line on who wrote it, as their identity choice allows, and whether as the writer or for the redactie. That line counts only on comments of the App's own bot account, and only in exactly the form Schrijver writes. What a user types is posted as one quote, code blocks included, so no line of it passes for that line on GitHub; Schrijver takes the quote off again when it shows the reaction. HTML and mentions in it are defused on every line, in code blocks too (an invisible word joiner after `<` and `@`, which changes nothing visible in code), so nothing in it closes the quote or notifies anyone, whatever GitHub takes for a code block. A name in that line always follows "naam: ", so it never reads as a codename or a GitHub login, and keeps only letters, digits and plain punctuation.
5. **Four eyes.** With the site setting "Vier ogen" on (the default) nobody merges a proposal they wrote in Schrijver: the one who opened it or signed it, or anyone whose identity signed one of its commits. Where Schrijver cannot tell (no or a malformed signature, a proposal made on GitHub and no linked account to compare with, a list of commits that may be incomplete) it treats the reader as the writer. A site admin may still merge; for now that is a linked GitHub account with admin permission on the repository, behind one function that a later definition of site admins replaces.
6. **One block says what now.** Under the title one tinted block holds the step bar, one sentence on what is expected of the reader and the buttons for it, per role: the writer, a member of the redactie, anyone else.

## Consequences

- A site that requires an approving review still needs a GitHub account for that approval; the proposal page says so in its own words instead of listing who approves. The way to GitHub ("Goedkeuren op GitHub", "Beoordelen op GitHub") is a button only for a reader who linked a GitHub account, and the page does not check their permission there. Anyone else reads that someone with rights on GitHub approves or merges there, and an editor is told to ask for an adjustment if something has to change.
- A member of the redactie who wrote the proposal has rows of their own, and is never offered a request for an adjustment of it. Where four eyes keep them from deciding they read that another member decides and can edit further; where they may merge (four eyes off, or a site admin) they get "Samenvoegen" and "Verder bewerken".
- Where GitHub cannot merge a proposal, the page offers no merge and says why in plain words: the page changed on the site since. The redactie can ask the writer for an adjustment; the writer reads that the change has to be made again, because Schrijver cannot update the branch, or that someone may solve it on GitHub. Send-in and a refused merge say the same in one line.
- A proposal with as many commits as GitHub lists is not merged in Schrijver by anyone, a site admin included: the page shows the row of a site that merges on GitHub, with the reason (the answer of four eyes goes first), and the merge refuses with a pointer to GitHub.
- Re-sending is the writer's: the endpoint refuses anyone else, an editor included, with a 403 that is logged like the other refusals.
- Comments that Schrijver posts on GitHub read "**Reactie van de redactie via Schrijver** (…)" with a hidden `<!-- schrijver -->` marker, followed by the reaction as a quote. Mentions in a reaction no longer notify anyone on GitHub.
- Four eyes in Schrijver rest on the identity trailers and the linked GitHub account. A member of the redactie known only by e-mail address cannot merge a proposal signed with a GitHub account or made on GitHub, because Schrijver cannot tell whether it is theirs. A writer whose e-mail address changed is no longer recognised, and rotating the pseudonym secret makes earlier anonymous proposals unrecognisable too. Branch protection on GitHub remains the hard guarantee, and anyone who can merge on GitHub can still do so there.
- Reactions, requests for an adjustment and re-sends share a limit of ten per minute per person, because what they post goes out under the App's name.
- The proposal page asks GitHub for its review decision, its comments and reviews and, for a member of the redactie who can decide, its commits (for four eyes, and to see whether the list is cut off at 250) on every view; these are not cached, so the page shows a decision as soon as GitHub has it. Where the proposal started, which "Wat er verandert" compares with, is one compare call per view, kept for ten seconds. Once the proposal is merged, its base branch holds the change: the compare then starts from the base branch as it was just before the merge, the first parent of the commit the merge put there (GitHub's `merge_commit_sha`), which holds for a merge commit, a squash and a rebase alike.

## Addendum, 2026-10-10: who wrote it, from Schrijver's own record

Point 5 treated the reader as the writer wherever Schrijver could not tell. On a site where most proposals come from GitHub, a member of the redactie known only by e-mail address could then decide on almost nothing. Four eyes now knows the writer instead of guessing:

1. **Schrijver records who writes.** Whenever it commits to a proposal for someone (the save that opens it, every later save through "Verder bewerken", a new page), it records their `sub` for that proposal in `proposal_writers`, with the time of their first commit. A recorded writer always counts, whatever GitHub says about the proposal or its commits: the first recorded writer of a proposal the App opened made it, every other recorded writer wrote along. A signature that is the reader's counts too.
2. **A complete record answers for what the App wrote.** When the record accounts for everyone the App signed for (no more different signers in the App's commits and the proposal than recorded writers), a signature in what the App wrote that is not the reader's, or that cannot be compared, no longer blocks. Without a complete record only a signature that is the reader's answers. Every other signature in what the App wrote is "cannot tell", because a writer's identity may have changed since they signed: another pseudonym secret (another instance of Schrijver, or a rotated secret), another linked GitHub account, another verified address. That holds for a proposal from before this table, one made by another instance of Schrijver, one where a record was not written, and one whose record went while it was still open. In these cases an editor who did not write the proposal cannot merge it in Schrijver either; a site admin can, and so can anyone who may merge on GitHub. The proposal page and the refusal of the merge say so to that editor, instead of that another member of the redactie decides: "Een beheerder van de site voegt het samen, of iemand met rechten op GitHub." (only the second where Schrijver does not merge it at all).
3. **What is made on GitHub belongs to its GitHub account**, but only for a proposal whose head is a branch in the site's own repository. Only accounts with write permission can push a branch there, they can merge on GitHub anyway, and GitHub lets no author approve their own pull request where the branch protection requires a review. Such a proposal opened on GitHub, or a commit pushed there (also one GitHub ties to no account), is the reader's only when it was made under their linked GitHub login; a reader without a linked GitHub account is not that writer. For a fork, a deleted fork or an unknown head the rule does not hold: Schrijver cannot tell, and refuses the merge as before.

Consequences:

- This replaces the third consequence above: an editor known only by e-mail address decides on proposals made on GitHub in the site's repository, and on proposals whose record is complete, whatever their signature.
- A site admin still merges despite four eyes; site admins have one definition (decision 0008): a beheerder of the site, a platform admin, or a linked GitHub account with admin permission on the repository.
- Errors fail closed. When the record, the App's account or a list of commits cannot be read, four eyes cannot tell and blocks; only an admin check that succeeds on its own lets a site admin through. A failed team or permission lookup makes no one editorial or admin. A record that cannot be written is logged and the save stands; the record is then incomplete, so the signatures decide for that proposal.
- "Cannot tell" also stays for a list of commits as long as GitHub gives, record or not; such a proposal is not merged in Schrijver at all (point 2).
- The record is personal data: while a proposal is open it links the proposal, also an anonymous one, to the SSO account of each writer. It goes when the proposal is merged or closed (GitHub's `pull_request` event, or the merge in Schrijver), and at the latest 183 days after the writer's first commit in it; also with the profile of someone who is forgotten, and with the site. A proposal still open after its record went is judged by its signatures (point 2).

## Note, 2026-10-10: the buttons by their present names

Where this decision says "Samenvoegen", "Opnieuw insturen" and "Vraag om aanpassing", the buttons read "Voeg samen", "Stuur opnieuw in" and "Aanpassing vragen" (which opens the form whose button, "Vraag om aanpassing", posts the request); "Insturen" reads "Stuur in". An action that acts at once is an imperative, one that leads on is a full verb, and a sentence that points at a button quotes its label ([woordenlijst.md](../woordenlijst.md)). The ids of the routes and statuses, the label `aanpassing gevraagd` and the comment on GitHub are unchanged.
