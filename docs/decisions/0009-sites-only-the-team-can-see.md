# 0009: Sites only the team can see

Date: 2026-10-10. Status: accepted. Builds on [0008](0008-people-in-schrijver-structure-in-the-site.md).

## Context

The owner wants Schrijver to work with private repositories, and asked: "waarom kan nu iedereen alles zien?" Schrijver reads GitHub with the rights of its App, not with the colleague's: most colleagues have no GitHub account, which is the point of Schrijver. So everyone who signed in could read every site: its pages, its proposals, their changes and their conversation. For a public repository that is fine, because all of it is public on GitHub too, drafts included. GitHub's access rules for a private repository do not reach into Schrijver, so there Schrijver itself has to decide who may see a site. Until now "Site toevoegen" refused a private repository as a stopgap.

## Decision

1. **Who sees a site is a site setting**: "Iedereen die inlogt" or "Alleen het team" (`zichtbaarheid` in the site settings, `iedereen` by default, with a database check). A public repository starts with "Iedereen die inlogt"; a private repository is always "Alleen het team", which its admins cannot change, and the beheer page says why. The server decides at every request by the repository's visibility as Schrijver last read it: Schrijver reads it with the repository whenever it loads the site, and on GitHub's `repository` events `privatized` and `publicized` it forgets it and loads the site again, so a repository that turns private is closed at once. A repository whose visibility Schrijver never read, could not read at its last try, or forgot and has not read again, counts as private. The choice of the site's admins is kept while it does not count: a repository that turns public again gets that choice back. A change is audited as the other settings are.
2. **A third role, Bijdrager** (`bijdrager`): sees the site and makes proposals, never decides. Bijdragers are invited and changed like the other roles, and nothing that checks editorial rights, four eyes or admin rights counts them. "Het team" is everyone with a role; the redactie and the beheerders decide.
3. **Who sees a site only its team sees**: the platform admins and the members of its team, in any role. On a private repository also someone whose linked GitHub account may read it (permission read, write or admin); write permission keeps counting as redactie, admin as beheerder. On a public repository everyone may read, so GitHub's answer says nothing about reading and only the team counts. A failed lookup lets no one in.
4. **One guard on the server.** Every request under `/sites/<id>` and `/api/sites/<id>` answers 404 before any route code runs, unless the site is one colleagues can work on and the user may see it: pages, their data, form actions, API endpoints and the file route, and every route added there later. A site that does not exist gets the same 404, so the answer tells nothing about which sites exist; a page shows the page that does not exist in the shell of the app, rendered by a route that runs no code of a site. A refusal is logged as `site.refused` with the actor's pseudonym. Every other place that names sites follows the same rule: the start page, Instellingen (the sites someone manages and the ways to sign per site), onboarding, the beheer page of a site, and the assistant, which takes a site in its request. The webhook stays as it is.
5. **"Site toevoegen" accepts a private repository** again, as a site only its team sees, whatever the form says. Step 2 checks the repository again when it is posted (its id, its visibility, the App on it) and refuses a name that now leads to another repository. A site only its team sees needs a first beheerder who gets in at once: the platform admin, or a colleague Schrijver knows by that verified address; an address that would only be invited is refused, as nobody but a platform admin could let that colleague in.

This changes point 4 of decision 0008: everyone signed in may propose on a site everyone sees; on a site only its team sees, whoever may see it.

## Consequences

- **Privacy.** On a site only its team sees, its pages, proposals, changes and conversation are read in Schrijver by its team, the platform admins and, for a private repository, the people GitHub lets read it. A draft in a private repository is not public: the editor, Help and "Over" warn about public drafts only for a public repository, and "Over" says who sees a site only its team sees. The team list stays personal data; a bijdrager is on it ([identiteit-en-privacy.md](../identiteit-en-privacy.md#who-reads-a-site-in-schrijver)).
- **The GitHub read rule** rests on GitHub's collaborator permission of the account (`GET /repos/{owner}/{repo}/collaborators/{username}/permission`), which reports maintain as write and triage as read. Schrijver keeps that answer for a minute per account and repository, because a page with images asks for every image: someone whose access GitHub withdrew may see the site for up to a minute longer.
- **The guard** decides on the site id the route itself reads. A test lists every route file under `src/routes/sites/[site]` and `src/routes/api/sites/[site]` and runs each through the server hook as a colleague outside the team: a route there that escapes the guard fails it, and so do a route beside `[site]` in those folders, a remote function there, and another route with a site in its path, until they are covered.
- Visibility follows GitHub through the `repository` event. Where that event is missed, a repository that turned private stays open to everyone who signs in until Schrijver reads it again: on a push to its default branch, an event on the App's installation, a restart, or at the latest at the reading of every site each quarter of an hour. The App must be subscribed to `repository` events ([een-site-aansluiten.md](../een-site-aansluiten.md#9-add-the-webhook)).
- On a public repository with "Alleen het team", a GitHub admin of the repository who is not on the team neither sees nor manages the site in Schrijver. A platform admin can add them.
